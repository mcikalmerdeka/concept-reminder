Let me break down your Dockerfile first:
```dockerfile
FROM python:3.7              # Uses Python 3.7 as the base image
COPY . /app                  # Copies all files from current directory to /app in container
WORKDIR /app                # Sets the working directory to /app
RUN pip install -r requirements.txt  # Installs Python dependencies
CMD ["python","app.py"]     # Command to run when container starts
```

Now, let's go through the key Dockerfile instructions:

1. **FROM**: Specifies the base image
   - Always the first instruction
   - Example: `FROM ubuntu:20.04`, `FROM node:16`

2. **WORKDIR**: Sets the working directory
   - All subsequent commands will run from this directory
   - Example: `WORKDIR /app`

3. **COPY/ADD**: Copies files from host to container
   - COPY is simpler and preferred
   - ADD can handle URLs and automatically extract archives
   - Example: `COPY . .` or `COPY package.json .`

4. **RUN**: Executes commands during build
   - Used for installing dependencies, updating packages
   - Example: `RUN apt-get update && apt-get install -y python3`

5. **CMD/ENTRYPOINT**: Specifies what to run when container starts
   - CMD can be overridden at runtime
   - ENTRYPOINT is harder to override
   - Example: `CMD ["npm", "start"]`

6. **EXPOSE**: Documents which ports the container listens on
   - Doesn't actually publish ports
   - Example: `EXPOSE 3000`

7. **ENV**: Sets environment variables
   - Example: `ENV NODE_ENV=production`

Best Practices:
1. Use specific base image tags (e.g., `python:3.9` instead of `python:latest`)
2. Combine RUN commands to reduce layers
3. Remove unnecessary files after installation
4. Use .dockerignore to exclude unnecessary files
5. Consider multi-stage builds for smaller final images

Common Patterns:
1. Development vs Production:
```dockerfile
# Development
FROM node:16
WORKDIR /app
COPY package*.json ./
RUN npm install
COPY . .
CMD ["npm", "run", "dev"]

# Production
FROM node:16-slim
WORKDIR /app
COPY package*.json ./
RUN npm ci --only=production
COPY . .
CMD ["npm", "start"]
```

2. Using environment variables:
```dockerfile

ENV APP_HOME=/app
WORKDIR $APP_HOME
COPY . .
CMD ["python", "app.py"]
```

Let me explain the CMD command format and its variations.

The CMD instruction in Dockerfile can be written in two formats:

1. **Shell form**: `CMD python app.py`
2. **Exec form**: `CMD ["python", "app.py"]` (using a list/array)

The exec form (list format) is preferred and recommended for several important reasons:

1. **Direct Process Execution**:
```dockerfile
# Exec form
CMD ["python", "app.py"]
# Runs 'python' directly as PID 1

# Shell form
CMD python app.py
# Actually runs '/bin/sh -c "python app.py"'
```

2. **Environment Variable Handling**:
```dockerfile
# Exec form with environment variable
ENV PORT=8000
CMD ["python", "app.py", "--port", "$PORT"]  # Won't work - variables not interpolated
CMD ["sh", "-c", "python app.py --port $PORT"]  # Correct way with variables

# Shell form
CMD python app.py --port $PORT  # Works directly
```

Let's look at common examples and their explanations:

```dockerfile
# 1. Running a Python script
CMD ["python", "app.py"]
# First argument: the executable (python)
# Second argument: the script name (app.py)

# 2. Running a web server
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
# Each argument is a separate string in the array
# uvicorn: the executable
# main:app: the application object
# --host and --port: server configuration options

# 3. Running npm
CMD ["npm", "start"]
# npm: the executable
# start: the command to run

# 4. Running with environment variables (needs shell)
CMD ["sh", "-c", "python app.py --port $PORT"]
# sh: the shell executable
# -c: flag to execute the following command
# The actual command as a single string

# 5. Running Jupyter notebook
CMD ["jupyter", "notebook", "--ip=0.0.0.0", "--no-browser", "--allow-root"]
# jupyter: the executable
# notebook: the subcommand
# Following strings: various configuration options
```

Common Patterns and Best Practices:

1. **Simple Script Execution**:
```dockerfile
# Good
CMD ["python", "script.py"]

# Avoid
CMD python script.py
```

2. **Web Servers**:
```dockerfile
# Flask
CMD ["flask", "run", "--host=0.0.0.0"]

# Django
CMD ["python", "manage.py", "runserver", "0.0.0.0:8000"]

# Node.js
CMD ["node", "server.js"]
```

3. **With Environment Variables**:
```dockerfile
# Method 1: Using shell form when you need env variables
CMD python app.py --port $PORT

# Method 2: Using exec form with shell (preferred)
CMD ["sh", "-c", "python app.py --port $PORT"]
```

4. **Multiple Commands**:
```dockerfile
# Using shell to run multiple commands
CMD ["sh", "-c", "python setup.py && python app.py"]
```

5. **Default Commands that can be Overridden**:
```dockerfile
# Can be overridden when running container
CMD ["python", "app.py"]

# Running container with different command:
# docker run myimage python different_app.py
```

Things to Remember:
1. Only the last CMD in a Dockerfile takes effect
2. CMD can be overridden at container runtime
3. Each element in the exec form array is a string
4. No shell processing in exec form (no environment variables, no pipe operations)
5. Use ENTRYPOINT instead of CMD if you want to ensure specific command always runs

Example combining ENTRYPOINT and CMD:
```dockerfile
# ENTRYPOINT defines the executable
ENTRYPOINT ["python"]

# CMD provides default arguments
CMD ["app.py"]

# Can be overridden like:
# docker run myimage other_script.py
```

This structure gives you flexibility while maintaining a default behavior. The ENTRYPOINT ensures Python is always the executable, while CMD provides the default script to run, which can be overridden when needed.
