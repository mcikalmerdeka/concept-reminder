# What “Database Migration” Actually Means (in Backend Dev)

In backend / full-stack development, **database migration = version-controlled schema changes**.

It’s about managing changes to the **structure** of the database over time, such as:

* Creating tables
* Adding/removing columns
* Changing column types
* Adding indexes
* Adding foreign keys
* Renaming tables

It is **NOT primarily about moving data between systems** (which is what data engineers usually mean by migration).

---

## 🔹 Example Scenario

Let’s say your app initially has this table:

```sql
CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    name TEXT NOT NULL
);
```

Later, product says:

> “We need user emails.”

So you add:

```sql
ALTER TABLE users ADD COLUMN email TEXT;
```

That change is a **migration**.

Now imagine:

* 3 developers
* Dev, staging, production environments
* CI/CD

You cannot manually run ALTER TABLE everywhere.

So frameworks like:

* Prisma
* Django
* SQLAlchemy
* TypeORM

…create **migration files** that are versioned and reproducible.

---

# How Developers Think About It

Think of it like:

> Git for your database schema.

Every schema change is:

* Saved as a file
* Versioned
* Replayable
* Reversible (sometimes)

---

# Prisma Example (TypeScript)

Prisma uses a schema file like this:

```prisma
model User {
  id    Int     @id @default(autoincrement())
  name  String
  email String?
}
```

Then you run:

```bash
npx prisma migrate dev --name add-email-to-user
```

Prisma:

1. Generates SQL behind the scenes
2. Creates a migration file
3. Applies it to your database
4. Tracks it in a `_prisma_migrations` table

You never manually write the ALTER TABLE.

# Python Example — SQLAlchemy + Alembic

In Python, migrations are commonly handled with:

* SQLAlchemy
* Alembic

---

## Step 1: Define Model

```python
from sqlalchemy import Column, Integer, String
from sqlalchemy.orm import declarative_base

Base = declarative_base()

class User(Base):
    __tablename__ = "users"
    
    id = Column(Integer, primary_key=True)
    name = Column(String, nullable=False)
```

---

## Step 2: Later You Add Email

```python
class User(Base):
    __tablename__ = "users"
    
    id = Column(Integer, primary_key=True)
    name = Column(String, nullable=False)
    email = Column(String, nullable=True)
```

---

## Step 3: Generate Migration

```bash
alembic revision --autogenerate -m "add email column"
```

Alembic generates something like:

```python
def upgrade():
    op.add_column('users', sa.Column('email', sa.String(), nullable=True))

def downgrade():
    op.drop_column('users', 'email')
```

Then apply it:

```bash
alembic upgrade head
```

# Why This Matters in Production

Imagine:

* You deploy backend code expecting `email` column
* Production DB doesn’t have it yet

💥 App crashes.

Migration ensures:

* DB changes are applied before code runs
* All environments stay in sync
* Schema history is trackable

# Important Difference (For You as Data Engineer)

In data engineering, migration often means:

* Moving from MySQL → PostgreSQL
* Moving warehouse Snowflake → BigQuery
* Lifting on-prem → cloud

That’s **infrastructure/data migration**.

In backend dev, migration means:

> Controlled schema evolution.
